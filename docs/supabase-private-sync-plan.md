# G検定：Supabase 自分専用同期（第1段階）設計案

状態：**設計のみ・未接続・未公開**。本番リポジトリ `gkentei-app` と現行プレビュー動作は変更しない。

## 目標と非目標
- 目標：本人が明示的に有効化した場合だけ、Safari / LINE経由 / iPad で解答履歴を同期。
- 非目標：友人の履歴の自動収集、全利用者の追跡、公開ランキング、管理者による友人の学習状況の閲覧。
- 既定状態は**端末内保存のみ**。クラウド通信はオプトイン後に限定。
- 初期段階は専用の検証Supabaseプロジェクトと**許可済み本人ユーザーIDのみ**。他ユーザーへの許可はしない。

## 現状調査
- 正式版 README によると履歴はブラウザ内に保存し、JSONバックアップ機能がある。端末間同期はない。
- このプレビューリポジトリの `index.html` は独立した保存キーを使い、現時点で正式版より古いUI/保存構造。実際の統合前に正式版の履歴フォーマット・問題ID・保存キーを読み直し、互換性を確認する。
- LINE内WebViewとSafariのストレージは別になる場合がある。

## 最小データ（検証用）
1レコード＝1解答。持つ項目は `event_id`（端末生成 UUID）、`user_id`（auth.uid）、`question_id`（既存問題ID）、`is_correct`（真偽）、`answered_at`（日時）、`created_at`（サーバー受信日時）。
氏名、メールアドレス、端末情報、IP等を**アプリ側の学習履歴テーブルに保存しない**（認証サービスが処理する情報は別）。
選択肢本文、問題本文は同期しない。

## 同期手順
1. 設定画面に「クラウド同期：オフ（初期値）」。
2. 本人がオンを選んだ時のみ、保存目的とデータ項目を説明して同意確認。
3. 登録許可した本人のみ認証を有効化。招待・本人確認の方式はアカウント作成後に決定。
4. 端末内JSONを事前エクスポート。端末データは削除しない。
5. 既存履歴は日時・問題IDに加え生成した event_id で識別し、**アップロード前にプレビュー**。競合は上書きせず追記と重複排除。
6. 初回アップロード成功後、クラウド履歴を読み込む。同期失敗時は端末内の学習機能を継続。
7. Safari、LINE、iPad で同一ログイン後に履歴一致を確認。ブラウザ間の認証状態は共有されない可能性がある。
8. オフにすると以後送信停止。既存のクラウド履歴を削除する操作は別途明示確認、バックアップと復旧手段を用意。

## セキュリティ必須条件
- DBの `public` テーブルはRLSを有効化し、本人IDかつ許可リスト登録済み以外は SELECT / INSERT できない。
- UPDATE / DELETE は初期段階で**許可しない**。保存は追記専用で event_id 重複時は無変更。
- 許可リストには利用者本人が自分を追加できない。サーバー管理者が管理する。
- `service_role`、DBパスワード、秘密鍵、認証管理トークンをフロントエンド・GitHub・Vercel公開変数に絶対に配置しない。
- 公開可能な anon/publishable key もRLSが正しいことを前提に使用。
- 試験：未ログイン、未許可ユーザー、別のユーザーID、異常なID、二重送信、オフ時の無通信、ネット切断時、復旧時。
- 非公開の本番データを使わず、ダミー解答でテストする。
- 自動バックアップが無料枠で提供される前提にしない。エクスポートと復旧を確認。

## 必須ゲート
- この設計書だけではクラウド保存は始まらない。
- Supabaseアカウント・検証プロジェクト作成 → Auth設定とRLS設定 → 検証版UI追加 → テスト → 明示的な承認を経て初めて正式版を検討。
- アカウント作成や接続に必要なシークレットは、チャットに貼らずSupabase/Vercelの公式設定画面で扱う。
